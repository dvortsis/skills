# Structure: a textbook-style guide in GitHub Markdown

The guide follows the document-builder's textbook user guide (chapter openers, objectives, task procedures with
results, worked examples, takeaways, check questions with answers, glossary, revisions, index), written as linked
Markdown pages that GitHub renders. `scripts/docs_tool.py sync` writes the generated parts (contents, numbering,
navigation, index); `scripts/lint_docs.py` checks everything else. The codes in brackets are lint checks.

## Files (in `docs/` unless the project already keeps docs elsewhere)

| File | What it holds |
|---|---|
| `README.md` | Guide home: title, purpose, who it's for, task finder, contents, what you need, about this guide |
| `01-<slug>.md` … `NN-<slug>.md` | Chapters, numbered from 01 without gaps (CHAPTER_FILES) |
| `appendix-a-answers.md` | Answers to every Check your understanding question (ANSWERS), when any chapter has questions |
| `appendix-<letter>-<slug>.md` | Other appendices, lettered after A (for example `appendix-b-settings-reference.md`) |
| `glossary.md` | One `##` heading per term, A to Z (GLOSSARY_ORDER) |
| `revisions.md` | Table: Version · Date · Change (REVISIONS) |
| `index.md` | Generated by `sync` from `<!-- index: ... -->` markers (INDEX) |
| `images/` | Screenshots the user supplied, and diagrams |

The project's top-level `README.md` links to `docs/README.md` with one line ("Setup guide: [docs](docs/README.md)").

- One `#` per page. Chapter H1 is `Chapter N: Title`; `##` headings are `N.M Title`; `###` headings are unnumbered.
  `sync` rewrites the numbers from the file order and fixes links to renumbered headings (NUMBERING).
- Headings in sentence case, as GitHub's own docs do; keep product names and UI labels as written (HEADING_CASE warns
  on Title Case).
- **What you will learn** right after the opener: 2–6 objectives that start with an observable verb (Choose, Set,
  Map, Check), never "understand" or "know" (OBJECTIVES, OBJECTIVE_VERB).
- **Key takeaways** as the chapter's last block before the navigation: 2–6 items (TAKEAWAYS).
- A Troubleshooting chapter skips both boxes.
- **Check your understanding** (optional per chapter, at least one in the guide): 2–4 questions about decisions, not
  trivia; each answered in Appendix A under the chapter's heading, same count (ANSWERS).

## Components

### Procedure (one task, start to finish)
```markdown
To map the data folder:

1. In the template, find **Appdata path**.
2. Set it to `/mnt/user/appdata/beacon`.
   **Result:** The path shows in the field without a red border.
3. Select **Apply**.
   **Result:** Unraid downloads the image and starts the container.
```
An intro line `To <goal>:`, then a numbered list. One action per step, verb first, UI labels in **bold** as on
screen, 2–12 steps (PROCEDURE_STEPS). At least the last step has an indented `**Result:**` line
(PROCEDURE_RESULT). Warnings go before the step they apply to.

### Command (only when there is no button for it)
```markdown
In the Unraid terminal (the **>_** icon at the top right of the web UI), paste:

    ```bash
    docker logs beacon --tail 50
    ```
```
The sentence before the block names exactly where to run it (COMMAND_WHERE); every block has a language tag
(CODE_LANG); values the reader must change are `<placeholders>` and are explained right after; no real secrets
(SECRET_LITERAL).

### Choice
A table whose first header is `Option` (or `Choice`, `Value`, `Mode`), with exactly one row marked `(recommended)`
(CHOICE_RECOMMENDED), followed by a `[!WARNING]` for any unsafe option that names the safe alternative
(UNSAFE_ALTERNATIVE).

### Setting (a template field or a settings-screen field)
Under a `##` heading that says Settings, Fields or Options, each field is a `###` heading with its label as shown:
```markdown
### Web UI port
The port your browser uses to open Beacon.

**Recommended:** `8484`. Change it only if another app already uses that port.

**Safe to change later:** Yes. Change the host side only; the container side stays `8484`.
```
Each field has **Recommended:** (SETTING_RECOMMENDED). Add **Unsafe:** with the safe alternative when a value is
risky. The settings reference appendix lists every field in one table: Setting · What it does · Recommended · Notes.

### Worked example
```markdown
> [!NOTE]
> **Worked example**
> You already run another app on port 8484. Set **Web UI port** to `8485`, apply, and open `http://<server-ip>:8485`.
```
At least one in the guide (WORKED_EXAMPLE).

### Alerts (GitHub's five kinds only; ALERT_KIND)
| Kind | Use it for |
|---|---|
| `[!NOTE]` | Context, objectives, worked examples |
| `[!TIP]` | A faster or safer way, key takeaways |
| `[!IMPORTANT]` | A requirement the reader must meet |
| `[!WARNING]` | A risk: data loss, exposure to the internet, leaked keys |
| `[!CAUTION]` | An action that can't be undone (deleting data, resetting) |

At most two alerts per section besides the two boxes (ALERT_DENSITY warns). The `> [!KIND]` line stands alone.

### Background
Longer explanations go in `<details>` with a `<summary>` that names the question it answers, or link to the concept
page or glossary (BACKGROUND_LONG warns on paragraphs over 70 words outside `<details>`).

### Figures
`![Alt text of four or more words](images/file.png)` then an italic caption line `*Figure 2.1: What it shows.*`
(IMG_ALT, IMG_MISSING). Only screenshots the user supplies; until then list each needed screenshot in
`docs/images/SHOTLIST.md` and report them as pending. Mermaid diagrams are allowed with one sentence before them
saying what they show.

### Troubleshooting
A table: Problem · Likely cause · Fix, ordered by how often it happens (TROUBLESHOOTING), in its own chapter or
appendix. Every fix is an action the reader can take, with the exact place to do it.

## Links and the index
- Relative links only between guide pages; every link and `#anchor` must resolve (LINK_BROKEN). Anchors follow
  GitHub's rule: lowercase, punctuation removed, spaces to hyphens (`## 2.1 Map the data folder` ->
  `#21-map-the-data-folder`).
- Link a glossary term to `glossary.md#term` the first time each page uses it (GLOSSARY_LINK warns).
- `<!-- index: term; other term -->` under a heading adds index entries pointing at that heading; `sync` builds
  `index.md` (A to Z, letter headings).
- `sync` writes the navigation footer on every page: previous · contents · next (NAV).

## Required parts of a guide (STRUCTURE)
Home, at least two chapters, a chapter on keeping the app safe (its title has "safe" or "secure"; SECURITY_CHAPTER),
troubleshooting, glossary, revisions, index; Appendix A when any chapter has questions. A settings reference
appendix when the project has settings or template fields (discover.py lists them; SETTINGS_REFERENCE warns).
