# Slide Deck

You write `deck.json`; the scripts handle layout, brand, charts and checks. Every deck is built on the generated master in the project's brand (`scripts/master.py` makes it at build time from the brand that `scripts/brand.py` resolves; no template file ships) in a modern minimal style: rounded cards, pill bars, tinted callouts and generous white space. Fonts are the project's own (the bundled Inter and JetBrains Mono only when the project names none), and every layout is measured with those font files, so spacing, card heights and marker alignment adapt to whatever font the deck uses. The theme sizes are the defaults (32pt headlines, 20pt body); text auto-fits down to set floors, and only the brand's role colors and their tints are used. Never hand-place shapes, paste chart pictures when you have the numbers, or edit the .pptx directly.

## 0. Preflight (first, before any other work)
Run `scripts/preflight.py` from this skill's folder (the folder containing this SKILL.md) with `python3` (or `python` on Windows; the commands below just say `python`). On `READY`, continue. If it fails or is missing, stop and say once: "The slide-deck skill loaded without its supporting files. Please attach `slide-deck.zip` to this chat, or ask the agent owner to re-upload it as a .zip." When the zip is attached, extract it, run preflight there, and run every command from that folder. Never hand-write, approximate or skip a script.

## Brand (right after preflight)
Run `python scripts/brand.py show --source deck.json` (before deck.json exists, run it from the project folder without `--source`). It prints the brand the build will use: a `BRAND:` line naming the brand and where it came from (`profile <path>`, `detected in <folder>` or `neutral defaults`), the role colors, fonts, logo, footer, any contrast adjustments, and `BRAND_CONTRAST`. Put the BRAND line in your reply. When it says neutral defaults, ask once whether the user has a logo, colors or brand guidelines; if they give them, write `brand.json` beside deck.json (or run `python scripts/brand.py detect --out brand.json` and edit it), check it with `python scripts/brand.py check brand.json`, and only then build. Never invent a logo or recreate one by drawing; with no logo the deck has none. Keep `deck.json` inside the user's project and call the scripts by their full path; a deck.json written elsewhere (the skill folder, a temp folder) can't see the project and builds neutral, so then pass `--brand` or set `BRAND_PROJECT` to the project folder. Lookup order, the profile format and the role colors: `references/brand.md`.

## Workflow (story first, slides second)
1. **Frame.** Get the audience, the goal and the big idea (one sentence). Set `meta.type`: `decision` when the deck asks for a decision, `inform` when it explains, trains, documents or updates. If you can't infer them, ask once in a single line. Read `references/storytelling.md`.
2. **Storyline.** Write the slides as takeaway titles in story order, answer first, and give each a `message` from the 18 types in `references/visual-selection.md` (point, number, numbers, change, comparison, flow, loop, sequence, plan, structure, tradeoff, options, status, questions, ideas, walkthrough, guidance, context). No layouts yet. Read the titles alone: do they tell the story?
3. **Choose layouts from the messages.** Run `python scripts/plan_deck.py storyline.json` for a first and second choice per slide that tells its message and keeps the deck varied. Pick by what the content really is; any layout serves any subject (an anatomy slide can explain a screen, an org chart or a building). Then draft `deck.json` and run `python scripts/lint_deck.py deck.json --story`: MESSAGE_FIT fails when a layout can't tell its message, and the rhythm and tone strips show the variety.
4. **Details.** Fields from `references/deck-schema.md`, brand and icon rules from `references/brand.md`, patterns from the examples in `assets/` (short, rhythm, variety, minimal, readiness and guide decks). Add a `takeaway` insight box to the 1–3 visuals that most need a so-what, and Tabler icons only where they help people scan.
5. **Screenshots.** Use only captures the user supplies, with no PHI or PII. When no capture exists, a deck may use a source-gated, stamped screen illustration supplied by an overlay skill (drawn from a layout spec, every label traced word for word to a saved source, stamped "Illustration, not a live screenshot") on a `screenshot` slide, if the stamp stays visible, the source line says "Illustration, not a live screenshot" (ILLUSTRATION_LABEL) and the figure passes the plain-language and general-example checks; it never closes the shot list; list it in the reply as an illustration. Never draw a screen yourself or show one that no source supports. Keep an existing screen-by-screen shot list; never replace it with a generic one. If a capture is missing, ask once for the named files and continue with `--draft`, which writes `<deck>.shotlist.md` (ID, screen state, target slide, callout positions, capture rules). An inform or training deck that walks through a screen on 5+ slides needs 3+ screenshot, annotated or anatomy slides, or that shot list (SCREENSHOT_SLIDES); report the screenshots as pending, never the deck as complete.
6. **Build.** Run `python scripts/build_deck.py deck.json --out <Name>.pptx [--draft] [--brand brand.json]`. It prints the BRAND line, runs the design gate first and refuses to build on any FAIL.
7. **Lint.** Run `python scripts/lint_deck.py deck.json --pptx <Name>.pptx [--draft] [--brand brand.json]` (it checks against the same brand the build used). Fix `deck.json` and rebuild until it reports 0 failed. Never deliver with a FAIL. The .pptx checks measure what a viewer sees: title widows (ORPHAN: last line of two words or fewer, or under a quarter of the width, measured as rendered: in the deck's own font files, or the fallback Inter when the project's font has no file here, taking the wider of that and the font a renderer substitutes), one-line titles on table, steps, matrix and comparison slides (TITLE_LINES), crowding under the title (TITLE_GAP), empty slides (EMPTY_SPACE) and half-empty cards (CARD_FILL). Plain-words checks: TELEGRAPHIC, HIGHLIGHT_REASON, RETRIEVAL_FORM, RETRIEVAL_ANSWER, NOTES_TAGS, TERM_CONSISTENT. Brand checks: only the brand's display and body fonts (FONT) and role colors (COLOR), the alert color only with a reason (ORANGE), the project logo on the cover (LOGO_MISSING; LOGO_NONE warns when the project has no logo) with its corner kept clear (LOGO_ZONE). Layout checks on the built file: ACCENT_STYLE, ACCENT_RADIUS, ACCENT_CONTRAST, MATCHED_HEADINGS, PAIRED_ALIGNMENT, TEXT_COLLISION, LAST_LINE_ORPHAN, HIGHLIGHT_SPLIT, LABEL_BREAK, STATUS_TAG, FOOTER_CONSISTENT, DRAFT_MARK, CORE_PROPS (warnings: CARD_FILL_BALANCE, PARALLEL_POINTS, EMPTY_BAND, TOP_GAP, MARKER_BUSY).
8. **Look.** Run `python scripts/render_preview.py <Name>.pptx` (it converts with LibreOffice, or with an installed PowerPoint on Windows); each run renders into a new folder with contact sheets of 4 slides, so never inspect an older render. View every sheet; open a slide full size when its sheet shows a possible problem and for small text. Record findings, fix `deck.json`, rebuild, then run `python scripts/visual_batch.py check <render folder> --log <file_key>.visual_qa.md` (FAIL VISUAL_BATCH). Steps and what to look for: `references/visual-review.md`. If preflight printed `WARN render: not available`, you can't view images, or it prints NOT RUN, skip the loop and report "visual review: not run (reason)".
9. **Deliver.** Save the .pptx to the output folder and give its link. Then add, in at most 6 lines: the BRAND line, the storyline (the titles), open items (the shot list if `--draft`), and the checks line (`LINT: n checks, 0 failed` plus `visual review: N pages on S sheets, F viewed full size, M findings fixed` or `visual review: not run (<reason>)`). Never paste slide content into chat.

## Revisions
Make targeted edits to `deck.json`, rebuild, re-lint, and re-deliver under the same name with the next version suffix (`_v2`). Keep `deck.json` (and `brand.json`, if you wrote one) next to the .pptx and offer it when the user wants to keep iterating. When a change retires wording, an example or a label, write each retired term and its replacement to `<file_key>.set.json` in the same step. When the user approves a deck that belongs to a set, list what carries over to the guide, quick starts and page (wording, examples, rules) and what stays deck-only (accent tabs, hollow dots, phase dividers, large single-number slides).

When a user asks for a look the schema can't express, build with a working copy of the builder, say so in the reply and write the patch into agent-creator instructions. Never edit the installed skill or the built .pptx.

## Rules
- One idea and at most one visual per slide. Body text of 40 words or fewer; detail goes in speaker notes, which every content slide has.
- Variety comes from layout, never from new colors, fonts or decoration: no same layout twice in a row (LAYOUT_REPEAT) unless the slides share a `series` (3 at most), no three slides of one archetype in a row, hero slides kept rare and never adjacent, no layout on more than 40% of slides, and background tone changed at least every five slides (tint band, split panel or hero).
- Titles are 4–15 word takeaway sentences, not labels. Write every heading and header in Proper Case (AP style); body text stays in sentence case. The builder converts headings and lint fails any that aren't.
- Numbers come only from the user's data or cited sources, rounded, each with a source line. Never invent data to fill a chart. Ask, or use a `statement` slide.
- Accents are rounded tabs behind the card (`meta.accent_style: "line"` restores flat strips); comparisons use matching dark headings and a neutral "vs" marker; process steps use hollow dots unless the order itself is the point (`numbered: true`). Accent words use `context` on dark slides and `card` on primary slides (ACCENT_CONTRAST).
- Every slide stands alone: labels and examples make sense without the speaker notes, and examples suit every domain unless the request names one.
- Primary is the focus and gray is context. The alert color only marks a missed goal, an unfavorable change or a failed save, and needs a reason.
- The logo, footer line and slide numbers come from the master. Never draw, import or move them, and keep the footer band and logo corner clear (enforced by lint). A logo comes only from the project or its brand profile.
- If a trigger is ambiguous (e.g. "make a summary"), confirm the user wants slides before building.

## Anti-slop (never)
Topic-label titles ("Overview", "Results"); "Agenda" slides in decks under 10 slides; ending on "Thank you" or "Questions?"; walls of bullets; two text-only slides in a row; pie, donut, 3-D, radar or rainbow charts; legends where direct labels fit; stock photos, clip-art, icons-as-decoration, decorative blobs or emoji; hard or diagonal shadows; unsourced or unstamped screen drawings presented as screenshots; generic shot lists ("the screen this slide walks through"); flat accent strips; arrows between compared options; PHI in any image; gradients and shadows; filler words (leverage, unlock, seamless, robust, synergy, empower, game-changing); unsourced numbers; an invented or redrawn logo; delivering with a FAIL or calling an unrun preview "checked".
