# Writing comprehensive and technical documents

- **Task-based structure.** Organize by what the reader needs to do (Open the Dashboard, Export Data), not by the system's menus. One task per section; concepts before the tasks that need them.
- **Answer first in every section.** The first sentence says what the section lets the reader do or know.
- **Procedures.** Start with the goal ("To export a filtered report:"). One action per step, verb first, UI labels in bold exactly as on screen. Put the result after the step that causes it. Put warnings before the step they apply to, never after.
- **Screenshots earn their place.** Show a screen when the reader must find something on it; crop to the relevant area; caption says what it shows; alt text describes it for screen readers. Never fake or recreate one.
- **Tables for lookup, prose for reasoning.** Use a table when readers compare or look up values (filters, fields, error codes); keep explanations in paragraphs.
- **Plain language.** Short sentences (aim for 20 words or fewer), active voice, second person ("Select Export"), present tense. Define every acronym on first use and add it to the glossary.
- **Consistent terms.** One name per thing across the document; match the product's labels.
- **Callouts sparingly.** At most two per section. Note = useful context; Tip = a faster way; Example = a worked case; Important = a requirement; Warning = risk of data loss, privacy or compliance issues.
- **Troubleshooting as a table:** Problem · Likely cause · Fix, ordered by how often it happens.
- **Version control.** Every release adds a revisions entry and bumps meta.version; the footer carries the version so printed copies can be checked.
- **Accessibility.** Real headings (they become PDF bookmarks and the contents), alt text on every figure, meaning never by color or icon alone.
